Stim 是一个开放的小型决策模型家族，基于 Qwen3.5 基座模型和 TypeSafe 的
[System One](https://docs.typesafe.ai/api) 协议构建。Stim 模型不生成文字答案，而是返回调用方选项上的概率分布：一个 state、一批带类型的问题、一个响应。

真正的差异不只在架构。Stim 将**权重、语料、训练配方和评估一起发布为一份可复现的记录**，让与项目无关的第三方也能重新训练这个家族，并重新推导已发布的分数。

> **状态：服务基础脚手架。** 目前已有的是软件包骨架、三个命令行入口、依赖边界和 CI。权重、语料、训练配方、评估、协议实现和 HTTP 服务都还不存在。标注为**计划中**的章节描述的是已经确定的设计方向，而不是已交付的行为。

## 亮点

- **输出决策，不输出聊天。** 模型的全部输出是调用方定义选项上的概率分布，因此概率可以被阈值化、用于路由，或升级给人工处理。
- **System One 接口面。** 目标是 `POST /v1/systemone`，支持 `noul`、`choice` 和 `score` 问题，以及 `GET /v1/models`，并通过 TypeSafe 官方 Python SDK 验证。
- **内部使用 Qwen3.5。** 家族围绕 Qwen3.5 Base 检查点设计：开放权重、宽松许可证、多个小尺寸，以及标准的 `transformers` / `peft` 工具链。[为什么选择 Qwen](#为什么选择-qwen) 说明了理由。
- **一份记录，四类产物。** 权重、语料、训练配方和评估作为一个带版本的单元发布，而不是四个互不相关的发布物。
- **仅限宽松许可证的语料。** 训练数据只使用允许无条件再分发的来源；share-alike 和许可证不明的来源被排除，缺口由合成数据填补。
- **双轨评估。** 公共可比性轨道用于和生态中的模型比较；独立的验证轨道完整发布，供第三方重新运行。
- **小到可以重训。** 家族规模受*复现者成本*约束，即一个外部第三方仅凭已发布配方达到同等量级所需的 GPU 小时数。
- **计划中的中文线。** 第一个语言变体是 `zh-v1.0.0`，与英文家族独立版本化，共享配方骨架，但不共享语料或评估。

## 为什么选择 Qwen

Qwen 不是顺手选来的依赖。基座模型决定了哪些东西可以再分发、哪些尺寸值得重训，以及这个家族能否支持不止一种语言。设计选择 Qwen3.5 Base 检查点，是因为它同时满足五个要求：

| 要求 | Qwen3.5 如何满足 |
| --- | --- |
| 许可证清晰 | Qwen3.5 Base 权重以 Apache-2.0 发布。适配器、微调权重和语料可以在没有使用领域限制的情况下再分发。 |
| 中性的起点 | `-Base` 检查点只经过预训练，没有在厂商的指令语料上做后训练。训练配方不会悄悄继承一段不公开的 SFT 阶段。 |
| 一个家族，而非单一尺寸 | Base 检查点提供 0.8B、4B 和 9B，正是 Stim 家族设计所覆盖的区间。成员尺寸可以跟随复现者成本，而不是重新谈判许可证。 |
| 标准工具链 | Qwen 受 `transformers`、`peft` 以及常见 LoRA/量化生态支持，训练和服务路径保持可移植。 |
| 多语言覆盖 | Qwen 的多语言预训练让中文线无需改变架构即可实现。中文线仍然需要自己的语料、校准和评估。 |

有两条边界必须说清楚：

- **Qwen 是基座模型，不自动等于教师模型。** 生成训练标签的教师模型是固定到具体 revision 的开放权重模型；闭源模型可以评判或过滤数据，但绝不提供标签。基座模型和教师模型是两个独立角色，并按产物记录。
- **基座许可证不等于语料许可证。** 每个语料来源都单独跟踪。Qwen 的 Apache-2.0 条款不会让第三方数据集变成可再分发的数据。

Qwen3.5 的混合注意力结构也会影响服务设计：部分层是循环层，会忽略注意力掩码，因此问题不能总是打包进一个块因果序列。Stim 的计划是让每个问题独立成行，并复用 state 缓存，从构造上保证问题之间的隔离。

## 计划中的模型家族

Stim 尚未固定成员列表。首个家族发布会公布确切的成员、参数量、适配器、温度、已验证上下文和分数。设计如下：

- 每个**成员**是家族中的一个尺寸，拥有自己的检查点或适配器，以及自己拟合的温度；
- 所有成员共享一份语料和配方骨架；
- **家族发布**会一起版本化所有成员；只有当共享输入未变时，单个成员才可以发布补丁版本；
- **语言变体**独立版本化，首个是 `zh-v1.0.0`。

架构是一个小型 Jev 风格决策模型：

```text
state ──► 渲染一次 ──► Qwen 主干（仅 prefill）
                          │
问题 1 ──► 分支 ──► 指针头 ──► 选项上的概率分布
问题 2 ──► 分支 ──► 指针头 ──► 选项上的概率分布
问题 3 ──► 分支 ──► 指针头 ──► 选项上的概率分布
```

模型不生成 token。主干只做 prefill；指针头将每个选项结尾的隐藏状态与问题的 decide 状态打分；softmax 将分数变成答案分布。同一请求中的问题共享 state，但彼此独立作答。每个成员有一个在留出池上拟合的标量温度，用于校准分布，但不改变哪个选项胜出。

## System One 兼容性

Stim 的兼容性主张有明确范围，而不是绝对的。承诺的目标是：

| 接口面 | 目标 |
| --- | --- |
| `POST /v1/systemone` | `noul`、`choice`、`score` |
| `GET /v1/models` | 已接受模型名的模型卡 |
| 官方 SDK | `typesafe-sdk==0.7.5` |
| `box` 问题 | 范围之外 |
| 图片与 multipart 输入 | 范围之外 |
| 262k token 输入 | 范围之外 |

排除 `box` 不是路由层面偷懒：它需要支持图片的 state、图像主干和坐标头。如果对 `box` 返回 422 却声称“完全兼容”，这个声明就没有意义。README、SDK 一致性测试和逐字段兼容矩阵应当表达同一件事。

派生量遵循公开的参考公式，而不是模型输出：

- **`noul`** 返回“是”的概率，没有 `confidence` 字段。
- **`choice`** 的置信度为 `(p_max − 1/K) / (1 − 1/K)`，其中 `K` 是选项数。
- **`score`** 的置信度为 `max(0, 1 − Σ p_i |i − m| / MAD_uniform)`，其中 `m` 是众数层级，`MAD_uniform` 是均匀分布围绕中心的平均绝对偏差。

未配置的 TypeSafe 客户端可能使用 SDK 的默认模型名连接。Stim 只把这个名字当作**兼容性别名**接受：它永远不会被列为家族成员，也不会被报告为正在服务的模型。

## 可复现记录

发布单位是一份记录，而不是一个模型文件：

| 产物 | 发布内容 | 验收标准 |
| --- | --- | --- |
| 权重 | 检查点或适配器、配置、拟合后的温度 | 可下载且许可证清晰 |
| 语料 | 记录、逐来源清单、出处、许可证 | 作为一等产物可下载 |
| 配方 | 脚本、超参数、计算量范围、随机种子 | 外部第三方能重训到同等量级 |
| 评估 | 条目级数据、清单、代码、参考分数 | 第三方能重新运行并复现分数 |

从生成提示重建语料属于透明度，但不是验收标准的一部分。验收标准是：语料可下载、配方可重训、评估可重跑。

评估分两条轨道运行：

| 轨道 | 用途 | 发布内容 |
| --- | --- | --- |
| 公共可比性 | 与 Kev、Decision Index、JevBench 比较 | 现有公开冻结套件；封存或私有部分不可重跑 |
| 验证 | 承载可复现性承诺 | 条目级数据、出处、清单、评估代码、参考分数 |

报告的数字使用扣除随机猜测后的 skill（chance-corrected skill）：0 表示随机猜测，100 表示完美，基线来自每个套件自己的记录。校准单独报告。标签打乱对照模型使用同一份语料，但在问题类型和选项数量内部打乱标签，用来展示成员的 skill 不只是记住了标签边缘分布。

## 与 Jev、Kev、AutoJev 的关系

- **Jev** 是 TypeSafe 的托管决策模型。Stim 是一个独立的开放家族，使用同一协议；它不是 Jev，也不使用 Jev 的权重。
- **Kev**（`jaredpalmer/kev`）是 Stim 用来衡量自身并借鉴约定的开放参考实现：小型模型配方骨架、评估纪律和净室兼容性方法。Stim 不包含 Kev 的代码、语料或运行时依赖；`NOTICE` 记录了这项设计参考。
- **AutoJev** 是另一个 Jev 风格模型的开放复现。它说明在汇总的公开数据上做全权重 SFT 只是入场券，而不是差异化优势。

## 快速开始

环境要求：Python 3.12 和 [uv](https://docs.astral.sh/uv/)。

```sh
git clone https://github.com/0xnicholas/Stim.git
cd Stim

uv sync
uv run pytest
```

`uv sync` 会安装三个工作区软件包和开发工具。加上 `--all-extras` 可一并安装训练和评估依赖。

PyTorch 不提供 Intel macOS 的 wheel。在该平台上，`stim-ai` 会跳过 torch 和 peft 依赖，软件包仍可导入，但无法执行模型。

### 命令行入口

| 命令 | 发行包 | 当前行为 |
| --- | --- | --- |
| `stim` | `stim-ai` | 输出帮助；`--version` 报告模型核心版本 |
| `stim-serve` | `stim-serve` | 输出帮助；`--version` 报告服务层版本 |
| `stim-systemone` | `stim-systemone` | 输出帮助；`--version` 报告协议层版本 |

```sh
uv run stim --help
uv run stim-serve --version
```

在协议层、模型层和服务层落地之前，这些命令都只是占位。

## 开发

在本地运行完整检查：

```sh
uv run ruff check .
uv run ruff format --check .
uv run mypy
uv run pytest
```

测试检查的是结构，而不只是行为：

- `stim-systemone` 只依赖 `pydantic` 和标准库；
- 导入 `stim_systemone` 不会加载 torch 或 FastAPI；
- `stim-ai` 保持训练和评估依赖可选；
- `stim-serve` 不会拉入训练或评估 extra；
- SDK 基线固定为 `typesafe-sdk==0.7.5`；
- 包的导入名与发行包名一致；
- 许可证和 NOTICE 正确署名所需来源。

CI 会在每个拉取请求上运行同样的命令，构建全部软件包，并验证三个 wheel 均可导入。

## 构建

工作区根目录是虚拟的，因此需要一次构建所有成员：

```sh
uv build --all-packages
```

每个软件包会在 `dist/` 下生成一个 wheel 和一个源码分发包。
